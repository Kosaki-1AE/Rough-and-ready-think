#Mine研究/プロンプトエンジニアリング 
- **整理日**：2026年10月16日
- **現行実装**：16Rooms Dance Robot **v1.3**
- **対象**：本研究のアイデア・設計上の決定事項・プロトタイプ実装・検証結果・今後の課題
- **位置づけ**：研究開発の引き継ぎ資料。理論の成立、性能改善、ロボット実機での安全性を実証した論文ではない。

> **一文で言うと**：ダンスの「お手本を見る → 動きを記憶・再生する → 自分が実行した場合を予測する → 実行結果との差を経験として残す → 分からなければ見直す」という循環を、16Roomsの状態遷移とBackroomsの経験記憶で構成し、将来的にNAO／Unitree G1へ接続する研究。

## 1. 研究の目的と方針

### 1.1 目的

ダンサーが音楽に合わせて身体を動かすときの経験的判断を、再利用可能な状態遷移・動作チャンクとして扱い、観測・予測・実測フィードバックによって改善できる仕組みを構築する。将来的には、MediaPipeで得た人間の動作をNAO／Unitree G1等のロボットの身体条件へ適応させる。

### 1.2 基本方針

1. **Roomの処理上の役割は定義するが、Coherence／Qualityなどに固定的な正解スコアを埋め込まない。** 判断基準は実際の観測と結果に基づいて育てたい。
2. **絶対条件は別管理する。** データ形式、関節ID、単位、ロボット関節制限、緊急停止といった条件を経験則で勝手に上書きしない。
3. **観測と想像を混同しない。** お手本の記録、再生、モデルによる予測、ロボット／人間の実測を区別する。
4. **分からなければ確定せず、再生・予測・再観察へ戻る。** 情報が不足したまま動作を強行しない。
5. **意思決定と動作実行を分離する。** 30msは現時点で強制しない。判断遅延を測定し、モーターの安定化制御とは分けて考える。
6. **オフライン・軽量を重視する。** 標準ライブラリで動く中核と、MediaPipe／OpenCVなどの追加依存を分離する。将来のC実装・学校用PCも考慮する。

## 2. 16Roomsの構造

![[ネオン式4×4ルート図解.png]]
### 2.1 16のRoom（Hex 0〜F）

| Hex | Room | 現在の役割の理解 |
|---|---|---|
| 0 | Input | 入力データを受け取る |
| 1 | Buffer | 入力データの一次確認 |
| 2 | Pool | 内容・候補を一時保持する |
| 3 | Queue | 候補・処理待ちを順序管理する |
| 4 | Motion | 入力と状態を踏まえた動作候補を作る |
| 5 | Stack | 意図した動作と状況を比較し、Poolから候補を扱う |
| 6 | Coherence | 行動・身体・音楽・周囲との整合性を評価する段階 |
| 7 | Capacity | Poolにある候補を確認する段階 |
| 8 | Jab | 保険となる暫定候補を提示する |
| 9 | Quality | 候補・暫定案・状況を踏まえ、出力可否を検討する |
| A | Twist | 別の可能性や変化を加えた候補を検討する |
| B | Stillness | 全体を俯瞰・再確認する。特にCoherenceとCapacityに注意する |
| C | Depth | Poolに残った内容を掘り下げる |
| D | Straight | Poolの候補から直接的・合理的な案を扱う |
| E | Output | 判断結果・出力を確定する段階 |
| F | Genesis | 最後に受け取った入力を参照する起点・循環点 |

※ Room名・概念は研究者の設計案に基づく。表の説明は処理仕様の整理であり、各Roomが実験的に独立した認知機能であることを証明したものではない。

### 2.2 8bitレジスタとBackrooms

```text
[ BB ][ O ][ RRRR ][ I ]   = 8bit
  2     1      4      1
```

- `BB`：Backroomsの候補／参照コード（2bit）。**経験全体の保存容量が2bitという意味ではない**
- `O`：出力フラグ（1bit）
- `RRRR`：Room番号（4bit、16状態）
- `I`：入力フラグ（1bit）
- **Backrooms**：過去の動作チャンク、適用状況、観測フィードバック、予測誤差などを別途保持する記憶領域
- 「経験3回で再利用経路へ入る」は現段階の**仮説的な実装ルール**。3回あれば正しいという科学的保証ではない
- 16Roomは表現上の状態数。**あらゆる処理が16遷移以内で完了するという普遍的な性能保証は未立証**

## 3. ダンス経験の最小表現

経験の中心は以下の**3要素**とする。

| 要素 | 意味 | 例 |
|---|---|---|
| **Entry** | 音楽のどこから振りに入るか | 1エイトの1拍目から |
| **Time** | 1エイト内の時間的な位置・長さ | 位相 `0.0〜1.0` |
| **Chunk** | 再利用可能な一連の動き | 6歩、トップロック、足の切り替え |

位相の基本例：

$$\phi(t)=\frac{t-t_{entry}}{T_{eight}}$$

- `t_entry`：振りの開始時刻、`T_eight`：1エイトの長さ。
- BPM120で4/4拍子、8拍を1エイトと数える場合は約4秒。ただし一般の楽曲に固定できない。
- お手本チャンク内の**開始姿勢・終了姿勢・途中経過**は、教師動画の対応区間を参照して得る。基本3要素に独立した「終了姿勢」という第四の項目を増やす必要はない。
- 比較するときは人間とロボットの身体構造・座標系の違いを補正する。終了姿勢が一致しても動作途中の連携が違う可能性があるため、**軌跡・リズム・身体部位間の協調**も評価対象とする。

## 4. Refrain・Simulation・Reobserveの追加

人間のダンス練習を参考に、次の3つを独立させた。

| 処理 | 役割 | 注意点 |
|---|---|---|
| **Refrain / Replay** | すでに観察・保存した振りを繰り返し再生する | 再生だけでは新しい実測経験にはならない |
| **Simulation** | 現在の状態と候補から、実行した場合の変化を予測する | 予測と現実を区別する |
| **Reobserve** | 不明点や欠落部分について、新しい観察を要求する | 再観察を要求しただけでは問題解決とはみなさない |

全体の学習サイクル：

```text
[音楽・お手本動画・本人/ロボットの観測]
                   |
                   v
      [Entry / Time / Chunk の整理]
                   |
                   v
           [16Roomsで候補検討]
                   |
             +-----+------+
             |            |
     [根拠あり]       [不明・不足]
             |            |
             v            v
      [Refrain]      [Reobserve要求]
             |
             v
      [Simulation（仮予測）]
             |
             v
       [候補・HOLDを判断]
             |
        （将来、実行）
             |
             v
  [実測値と予測・お手本との差を記録]
             |
             v
         [Backrooms更新]
```

- `HOLD`時には `REPLAY`／`SIMULATE`／`REOBSERVE` 等を検討できる。
- ReplayやSimulationを繰り返しただけで「成功経験」を増やさない。
- 再生回数を無制限に増やすのではなく、得られる新情報の有無も今後の設計対象とする。
- **人間の実際の神経処理を再現できたと主張するものではなく、学習行動の機能的なモデル化**である。

## 5. NAO・Unitree G1との関係

### 5.1 将来の接続構想

```text
MediaPipe / 33ランドマーク
            |
      人体の時系列特徴
            |
   ダンスチャンク＋16Rooms
            |
   身体構造に合わせたRetargeting
            |
    安全性を確認した動作軌道
            |
      NAO / Unitree G1
            |
 関節状態・IMU・接地等の実測
            |
      予測誤差と経験更新
```

- URDFを利用して関節の親子関係、軸、可動範囲、基準の相対座標を読み取る。
- 必要に応じて座標を `x+iy` など複素平面へ射影して分析する。**複素数への射影だけで3D姿勢や左右方向を完全表現できるわけではない**。
- MediaPipeの人体骨格とNAO/G1の関節数・可動域は異なるため、実際の動作には姿勢の変換、逆運動学、支持状態・バランス・接地の検討が必要。
- **URDFのローカル原点は、それだけでは実行時のワールド座標でもセンサー観測値でもない**。
- ブレイキンのヘッドスピン／ホローバック等を実機へ直接指令しない。安全確認済みの上半身・低リスク動作から段階的に検討する。

### 5.2 実機の制御と切り離すこと

16Roomsは候補提案や学習を担当する予定だが、低レベルの安定化制御、速度・トルク制限、関節制限、非常停止を置き換えるものではない。現行v1.3は**ロボットへのモーター指令を送信しない**。

## 7. v1.3の実装状況（コードから確認できる範囲）

### 7.1 統合実行

配布フォルダ `16rooms_dance_robot_v13` の例：

```bash
python pipeline_v13.py \
  --input sample/observations.csv \
  --reference sample/reference.csv \
  --mapping sample/mapping.json \
  --urdf sample/mini_robot.urdf \
  --feedback sample/feedback.csv \
  --entry-ms 0 --eight-ms 4000 \
  --memory output/v13_backrooms.json \
  --out output/v13
```

- コアは**Python 3.8以降の標準ライブラリ**を利用する構成。
- `live_integrated.py` にはOpenCVと互換性のあるMediaPipeが別途必要。
- `audio_clock.py` はPCM WAVから音量変化によるオンセット**候補**を抽出する。自動で拍子・小節・正確な1拍目を認識するものではない。
- `--entry-ms` と `--eight-ms` は利用者が指定する構成。自動同期と混同しない。

### 7.2 主なファイル

| ファイル | 用途 |
|---|---|
| `pipeline_v13.py` | CSVデータを一通り接続する統合入口 |
| `rooms_v11.py` | 16Rooms、Backrooms、簡易Retargeting、URDFなどの中核 |
| `mental_loop.py` | Refrain・Simulation・Reobserve |
| `live_integrated.py` | 動画／カメラ入力から統合処理へ渡す入口 |

| `extract_mediapipe_batch.py` | 骨格ランドマーク抽出 |
| `audio_clock.py` | WAVの音量変化から時間候補を抽出 |

### 7.3 主な出力

- `aligned.csv`：時刻／Entry／1エイト内位相の整列。
- `catalog.csv`：チャンクの登録状況、お手本開始・終了姿勢、取得できた区間。
- `decisions.csv`、`room_history.csv`：Room履歴、判断状態、8bitレジスタ等。
- `proposals_NOT_FOR_HARDWARE.csv`：実機に送らない候補角度。
- `refrain.csv`：保存済みのお手本の再生・区間内補間。
- `imagined_NOT_FOR_HARDWARE.csv`：単純な関節追従モデルによる予測。
- `requests.csv`：再観察の要求・新しい観測が到着したかの照合。
- `mental.csv`：再観察／仮予測などの選択履歴。
- `experience.csv`、`stats.csv`、`backrooms.json`：実測ベースの記録・記述統計・記憶。
- `summary.json`：処理件数等のサマリー。実機指令数は0。

### 7.4 検証済みと未検証の境界

**確認できたこと**：2026-10-16に同梱ソース上で `python -m unittest discover -p 'test_v*.py' -q` を実行し、**20テストすべて成功**した。v1.3の同梱サンプルは合成データであり、予測と検証済み実測を区別している。

**確認できていないこと**：実カメラ／実動画への頑健性、実際のダンサーでの識別・再現精度、オンライン学習の有効性、NAO／G1への実用的動作変換、リアルタイム性、実機での動作安全性。コードの統合完了と研究課題の解決は別。

## 8. 現時点で残る課題（物理シミュレータ・実機以外も含む）

1. **音楽同期の高度化**：実際の拍・ダウンビート・テンポ変化・映像との整合を自動推定する。
2. **チャンクの自動発見**：事前に名前を付けず、動作時系列から振りの区切り・繰り返し・遷移を発見する。
3. **予測モデルの経験学習**：固定の一次遅れ式の代わりに、実測を使って動作・身体連携を予測するモデルを育てる。
4. **能動的な再観察**：CSVに要求を書くだけでなく、必要な範囲を自動抽出・追加観測・再推論する。
5. **人間→ロボットの運動学的変換**：3D姿勢、遮蔽、座標校正、逆運動学、実行可能な軌道生成を改善する。
6. **実データ評価**：6歩などの動画を使い、経験記憶あり／なし、リフレインあり／なし、再観察あり／なしを比較する。
7. **低スペック環境での検証**：処理時間、メモリ使用量、Pythonバージョン／MediaPipe依存の確認。Python 2.x対応やC移植は未実装。
8. **物理シミュレータと実機**：今回は対象外。将来、安全な環境・既存制御器と段階的に接続する。

## 9. 次の実験設計案

**対象をまず1つ（例：6歩）に絞る。** お手本と本人の映像を同条件で収集し、音楽のEntry・Time・Chunkを揃え、最低限次を比較する。

| 比較条件 | 主な確認事項 |
|---|---|
| 記憶なし vs Backroomsあり | 反復によって予測／再現誤差が変わるか |
| Replayなし vs Replayあり | 時間・位相を揃えた再参照が効くか |
| 再観察なし vs 再観察あり | 欠落・誤認識を減らせるか |
| 単純予測 vs 経験で更新した予測 | 未使用データでも予測改善が再現するか |

想定する評価指標：チャンク境界の一致率、音楽位相ずれ、姿勢／関節角度誤差、予測誤差、再観察要求数、HOLD率、判断遅延、記憶量。**評価指標は学習目標・検証方法として定義し、Room内部の固定的な正解式と混同しない。**

実験時には、実測とシミュレーションを別ファイル・別ラベルで記録し、トレーニングに使った動画と検証用の動画を分ける。

## 10. 研究上の主張をどこまで言えるか

- **現時点で言える**：状態遷移・チャンク参照・簡易予測・再観察要求・実測と仮予測の区別を備えた、オフラインの検証用プロトタイプを構築し、合成データ上の自動テストを通した。
- **まだ言えない**：人間と同じ学習機構を再現した、16Roomsが一般に最適、未知のダンス動作を完全自律習得する、NAO/G1で安全に再現できる、30ms以内に必ず判断できる、など。
- **将来の主張候補**：経験記憶・再生・仮予測・再観察の組合せが、特定条件下でダンス動作の予測誤差や模倣精度を改善することを、比較実験で示す。

## 11. 引き継ぎ用の短いまとめ

**研究テーマ**：16RoomsとBackroomsを利用した、ダンス動作の経験的学習・再観察・動作候補生成の研究。

**経験表現**：`Entry / Time (1エイト) / Chunk` の3要素を基本とし、お手本チャンクから開始・終了姿勢を参照する。

**16Roomsの担当**：処理の段階・候補選択・保留・履歴管理。Roomごとの固定正解スコアは原則置かず、絶対条件は守る。

**Backroomsの担当**：チャンクと経験・観測誤差を保存。未検証の予測は「成功経験」に数えない。

**学習ループ**：`Observe → Refrain → Simulate → Decide/HOLD → Reobserve → (将来Execute) → Feedback → Memory`。

**実装到達点**：**v1.3** のオフライン統合パイプライン。標準ライブラリ主体のコア、別途依存するカメラ入力、WAVオンセット候補、簡易姿勢提案、Backrooms、再生・仮予測・再観察要求、CSVログ。**20/20自動テスト成功（合成データ）**。

**最優先課題**：実動画での動作確認、音楽・チャンクの自動解析、実測データからの予測学習、能動再観察、検証可能な比較実験。

**現時点で対象外**：本格的物理シミュレータ、実機への指令・制御。候補CSVをそのままロボットへ送信しない。
