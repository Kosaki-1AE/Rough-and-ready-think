# 資料から何を抽出したか

基準資料：`261004_理論がガチで、完成したぁぁぁ.md`。
末尾の修正後の式と処理順を実装の基準としています。

## 対応

| 資料 | 実装 | 扱い |
| --- | --- | --- |
| Room R_t | `State.room` | 分野によらない整数ID |
| 責任 b3b2 | `Decision.responsibility` | 0..3。意味付けは分野側 |
| 局所操作 b1b0 | `Decision.operation` | 打つ・弾く・外す・置くの4分類 |
| x_t = Φ_R_t(b3b2, b1b0) | `Domain.operate()` | 観測と状態も参照可能な拡張口 |
| m_t = D(b3b2, b1b0) | `route_decision()` | 末尾に示された4象限の判定 |
| R_t+1 = Γ(R_t, x_t, m_t) | `Domain.transition()` | 次Room、状態、Feedbackを返す |
| Observe → 責任 → 操作 → Router → 次Room → Observe | `Engine.step()`の反復 | 毎回観測し、最後に状態を更新 |
| 上位4/3/2bit | `room_bits=4/3/2` | Room範囲を検証 |
| 下位4bit | `Decision.nibble` | `(responsibility << 2) \| operation` |
| 1, i, -1, -i | `Operation.complex_unit` | 対応表。力学や数値演算の規則ではない |
| 結果4bit | `OperationResult.result_code` | 未定義のため省略可能な別欄 |

資料末尾のΓの引数には`t_t`表記がありますが、直前の操作結果`x_t`を受ける拡張口として
実装しています。時刻そのものも`Observation.timestamp`から参照できるため、結果と時刻を
別々に扱えます。これは実装上の解釈であり、原資料の数式の同一性を実証したものではありません。

## コアへ固定しなかったもの

- 4つの責任コードの具体的意味、評価軸や観測地点の名前。
- 各Roomの意味、Room同士の接続、退出の境界条件。
- Straight/Jab/Twistの具体的な出力、未処理の保持方法、観測者による回収方法。
- 時刻から何を判断するか、タイムアウト、遷移を保留する期間。
- `M_t, P, Ms, F, O, T, S`等の未確定なデータ構造や演算。
- 「遷移2」の確保・試行・正規化・方向確定の具体的アルゴリズム。
- 横・縦・高さ・抗力に対応する量の単位・計算法。
- 結果4bitの意味、次サイクルの入力への具体的符号化。

これらは`State.data`、観測、操作結果、Feedback、4つの分野メソッドで追加できます。
これにより未確定の意味をコアに埋め込まず、分野ごとの実装を別ファイルに置けます。

デモのRoom接続やダンスの意味付けは例示です。特定のビット値が人間の意図に一意に
対応することや、実際のダンサーがその過程を辿ることは、この実装からは確定しません。
